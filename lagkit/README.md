# lagkit — обработка лагов публикации факторов

В витрине значение фактора записано на свою **отчётную дату**. Модуль переносит его на дату,
когда значение **реально стало известно**. Если обучать модель на витрине как есть, в строке
«30.01» она видит показатель ЦБ «за 30.01», хотя опубликован он примерно через месяц. Это утечка
будущего (look-ahead bias): на истории модель выглядит лучше, чем потом работает в бою.

Модуль — самодостаточная папка. Её копируют в корень проекта и импортируют без установки:

```python
from lagkit import LagProcessor

lp = LagProcessor(master="master.xlsx", data="vitrina.csv", config="lag_config.yaml")  # config можно не задавать
lp.lags                          # factor, data_frequency, object_lag, lag_source, layout
lp.raw()                         # витрина, отфильтрованная по master
lp.journal(layout="long")        # журнал доступности: у каждого значения его available_date
X = lp.known()                   # таблица известных значений: идёт в обучение и предикт
lp.trace("factor_name")          # одна таблица DATE | raw | journal | available_date | is_filled | known
lp.diagnostics()                 # проверки и предупреждения
lp.save(view="known")            # пишет представление, таблицу лагов и диагностику
```

`master` и `data` принимают путь (`.csv`/`.xlsx`) или готовый `pd.DataFrame`. Кроме класса есть
функция `build_views(master, data, config)`, которая возвращает словарь
`{raw, journal, known, lags, diagnostics}`, и запуск из командной строки:

```bash
python -m lagkit --master master.xlsx --data vitrina.csv --config lag_config.yaml --view all --format csv
```

**Зависимости:** Python ≥ 3.9, `pandas` ≥ 1.5, `numpy`; для `.xlsx` нужен `openpyxl`.
Необязательные пакеты: `pyarrow` (запись в parquet) и `pyyaml` (конфиг в YAML). Без них модуль
работает и сообщает о нехватке пакета только тогда, когда вызвана функция, которой он нужен.

## Входные данные

**Master-файл** содержит колонки `factor`, `data_frequency` и `object_lag`, лишние колонки
игнорируются.

- `data_frequency` — `м`/`н`/`д`. Латинские `m`/`w`/`d` и любой регистр тоже принимаются.
  Другое значение — ошибка со списком проблемных строк.
- `object_lag` — неотрицательное целое число календарных дней. Значения `2`, `2.0` и `"2"`
  принимаются. Если поле пустое, берётся лаг по умолчанию. Дробное, отрицательное или
  нечисловое значение — ошибка с именем фактора. Нулевой лаг допускается с предупреждением.
- Повтор `factor` — ошибка.

**Витрина** — дневная широкая таблица: колонка `DATE` и колонки факторов.

- Из витрины берутся только факторы из master. Фактор, которого нет в витрине, исключается
  с предупреждением; при `strict: true` это ошибка.
- Даты разбираются в формате `ДД.ММ.ГГГГ` или ISO, либо по `date_format`. Если дату не удалось
  разобрать или она повторяется, это ошибка. После чтения строки сортируются по дате.
- Значения приводятся к числу; строки вида `"1 234,5"` понимаются. Сколько ячеек не удалось
  привести к числу, видно в диагностике (`non_numeric`).
- Для csv разделитель (`,`/`;`) и кодировка (utf-8, при неудаче cp1251) определяются автоматически.

## Логика: от даты отчёта к дате доступности

**Дата отчёта** (`report_date`) — строка, где у фактора появилось новое значение.
**Отчётный блок** — серия строк с тем же значением, начиная с даты отчёта. Блок заканчивается,
когда значение меняется или встречается пустая строка.

```
available_date = report_date + object_lag (календарные дни)
```

Дата доступности одна на весь блок: середина блока — продолжение того же отчёта, а не новый
отчёт.

Пример из ТЗ, лаг 2 дня:

| DATE  | значение | available_date | is_filled |
|-------|----------|----------------|-----------|
| 01.01 | 1        | 03.01          | False     |
| 02.01 | 1        | 03.01          | False     |
| 03.01 | 2        | 05.01          | False     |
| 04.01 | 2        | 05.01          | False     |
| 05.01 | 2        | 05.01          | True      |
| 06.01 | 2        | 05.01          | True      |

Таблица известных значений: на дату t стоит значение блока с наибольшей
`available_date ≤ t`, то есть 03.01 → 1, 04.01 → 1, 05.01 → 2, 06.01 → 2. Строки 01.01 и 02.01
пустые; при `drop_leading_empty: true` они удаляются.

**Как находятся даты отчёта.** Правило одно для обеих раскладок витрины:

- **`м`, `н`:** дата отчёта — непустая строка, у которой предыдущая строка пустая или значение
  отличается от предыдущего (больше чем на `value_tol`). В плотной раскладке (значение
  протянуто до следующего отчёта) это первая строка блока. В разреженной (значение стоит только
  в дату отчёта) — каждая непустая строка.
- **`д`:** каждая непустая строка — отдельный отчёт, даже если значение не изменилось.

Раскладка (`dense`/`sparse`/`daily`/`mixed`/`empty`) определяется только для отчёта и
диагностики. В расчёт значений она не входит, поэтому ошибка в её определении значения не портит.

**Почему не `shift(lag)`.** Для плотной раскладки и полного календаря значения в `known`
совпадают с `data[f].shift(lag)`, и тест это проверяет. Но построчный сдвиг даёт неверный журнал
(строке 02.01 он присвоил бы дату доступности 04.01), сдвигает пустые строки разреженной
раскладки и ломается на дырах в календаре: сдвиг на N строк не равен сдвигу на N дней. Поэтому
`known` строится через `pd.merge_asof(..., direction="backward")` по `available_date`. Если
`available_date` попадает на дату, которой нет в витрине, значение появляется в ближайшую
следующую дату.

**Протягивание.** Пустые строки после блока получают значение и `available_date` последнего
отчёта, а в журнале у них `is_filled=True`. Так обрабатываются хвост витрины, сбой загрузки
(в том числе несколько пропущенных периодов подряд) и промежутки разреженной раскладки.
Протягивание не ограничено. Ограничить его можно параметром `ffill_limit` (в днях от
`available_date`).

**Смысл `available_date` в журнале.** У собственной строки (`is_filled=False`) это дата, когда
стало известно значение этой строки. У протянутой — дата, когда стало известно последнее
значение, которое можно подставить на эту дату.

## Лаги

- Если `object_lag` в master заполнен, используется он (`lag_source=master`).
- Если пуст, лаг равен одному периоду частотности: `м` → 30, `н` → 7, `д` → 1 день
  (`lag_source=default`, переопределяется через `default_lags`).
- Лаг прибавляется в календарных днях, без учёта выходных и праздников.
- `lags_override: путь/к/lags.csv` замораживает таблицу лагов прошлого запуска. Так обучение
  и предикт используют одни лаги, даже если master изменился.

Снимок витрины тоже несёт информацию о лаге и используется для проверки, а не для выбора лага.
Пусть T — `snapshot_date` (по умолчанию максимальная дата витрины), r_last — дата последнего
отчёта, P — период частотности. Тогда должно выполняться `T − r_last − P < lag ≤ T − r_last`.
Слишком малый лаг даёт предупреждение (риск утечки на краю данных), слишком большой — info
(теряется свежая информация).

## Представления и форматы

| Представление | Широкий (`wide`) | Плоский (`long`) |
|---|---|---|
| `raw` | `DATE`, по колонке на фактор | `DATE`, `factor`, `value` |
| `journal` | `DATE`, пары `<f>`, `<f>__available_date` (+ `<f>__is_filled` при `journal_fill_flag`) | `DATE`, `factor`, `available_date`, `value`, `is_filled` |
| `known` | `DATE`, по колонке на фактор | `DATE`, `factor`, `value`, `available_date` |

- Широкий формат — это `pivot` плоского, поэтому форматы не расходятся.
- В плоском формате строки с пустым значением не пишутся; `keep_empty: true` их сохраняет.
- Календарь `known` по умолчанию — даты витрины от первой до `snapshot_date`; `calendar: daily`
  даёт все дни этого интервала. Если снимок задан позже последней даты витрины, он
  добавляется последней строкой.
- Колонка даты в `known` называется `known_date_col` (по умолчанию `DATE`).

`save()` записывает в `output_dir` три файла: `<view>_<layout>.<ext>`, `lags.<ext>` и
`diagnostics.<ext>`. Особенности форматов:

- **csv:** utf-8, даты в формате `ГГГГ-ММ-ДД`.
- **xlsx:** если таблица не помещается на лист (больше 1 048 576 строк), запись завершается
  ошибкой, а не обрезает данные.
- **parquet:** нужен `pyarrow`.

## Конфигурация

Все ключи и значения по умолчанию собраны в [`example_config.yaml`](example_config.yaml).
Конфиг передаётся одним из способов:

- путь к `.json`/`.yaml`;
- словарь;
- `LagConfig(...)`;
- `None` — используются значения по умолчанию.

Неизвестный ключ, в том числе в секции `diagnostics`, — ошибка.

## Диагностика

`lp.diagnostics()` возвращает таблицу с колонками `factor`, `check`, `severity`, `message`,
`details`. Те же сообщения пишутся в логгер `lagkit` стандартного `logging`.

| check | уровень | что означает |
|---|---|---|
| `leak_invariant` | error, исключение | В `known` нашлось `available_date > DATE`. Это ошибка в коде модуля, а не в данных |
| `missing_reports` | warning | Интервал между отчётами больше `gap_factor` периодов. В `details` — даты и число пропущенных периодов |
| `lag_below_snapshot_bound` | warning | Лаг мал по проверке снимка: риск утечки на текущем краю данных |
| `lag_above_snapshot_bound` | info | Лаг избыточен: теряется свежая информация |
| `frequency_too_high` | warning | У `м`/`н` медианный интервал меньше половины периода |
| `daily_rarely_changes` | info | Фактор `д` меняется реже раза в неделю |
| `mixed_layout` | info | Витрина меняла способ хранения фактора |
| `stale` | warning | Последний отчёт старше снимка больше чем на `stale_periods` периодов + лаг. Для такого ряда проверка лага по снимку не выполняется |
| `missing_factor`, `empty_factor`, `non_numeric` | warning, при `strict` — ошибка | Проблемы входных данных |
| `zero_lag`, `lag_override_missing` | warning | Нулевой лаг; фактора нет в `lags_override` |

## Допущения и границы применимости

- **Лаг постоянен во времени.** Праздничные сдвиги публикаций и смену регламента источника
  модуль не учитывает. Поэтому в отдельные даты истории значение может появиться в `known` на
  несколько дней раньше реального. Консервативный лаг уменьшает этот риск, но не устраняет его.
- **Дата отчёта определяется по данным** — это первая строка блока. Если в плотной раскладке
  новый отчёт `м`/`н` совпал по значению с предыдущим, блоки склеиваются. Значения в `known` от
  этого не страдают, но `available_date` в журнале и счётчик пропусков для такого блока
  неточны.
- **Витрина хранит последнюю версию значения.** Если источник пересматривает данные (ВВП,
  платёжный баланс), в истории стоят пересмотренные числа, которых на дату доступности ещё не
  было. Это остаточная утечка: без архива версий (vintage) её не устранить, и модуль этого не
  делает.
- **Пустая ячейка означает «не опубликовано», а не ноль.** Если в витрине ноль закодирован
  пустотой, модуль это не различит.
- **Лаг по умолчанию для месяца — 30 дней**, хотя месяцы длятся от 28 до 31 дня. Где это важно,
  лаг задаётся в master явно.
- **Частотности ограничены `м`/`н`/`д`.** Квартальные и годовые ряды обрабатываются, потому что
  даты отчёта берутся из данных: их можно отметить как `м` и задать лаг в master явно. Но
  диагностика пропусков будет давать по ним ложные `missing_reports`, пока не добавлены
  частотности `к` (90 дней) и `г` (365 дней).
- **Проверки по снимку опираются на допущения:** витрина обновлена на дату снимка, отчёты идут
  ровно с шагом периода, следующий отчёт не пропущен. Поэтому они только предупреждают и не
  меняют лаг.

## Тесты

```bash
pytest lagkit/tests
```

Тесты используют только синтетические данные и покрывают все критерии приёмки раздела 10 ТЗ,
включая производительность (600 факторов × 5 000 дат) и переносимость (копия папки во временный
каталог).
